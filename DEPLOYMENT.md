# Развёртывание

> Единственный файл в репозитории на русском языке, и это осознанно. Всё остальное — код,
> комментарии, `CLAUDE.md`, `LAUNCH-CHECKLIST.md` — по-английски, как требует `CLAUDE.md`. Этот
> документ отличается тем, что его **выполняет человек руками**, а не читает агент между
> сессиями. Не переводите его обратно. Идентификаторы, команды, имена переменных и путей
> остаются английскими: это не проза, а то, что набирают в терминале.

Написано 2026-08-16. До сих пор приложение, база и воркер работали на одном ноутбуке: не было ни
`Dockerfile`, ни `vercel.json`, ни CI, а `docker-compose.yml` поднимает только Postgres.

**Делать это на тестнете, задолго до запуска токена.** Репетиция и есть смысл: в день T-0 должны
меняться адреса, а не архитектура. Плюс главная продуктовая дыра — отсутствие публичного
трек-рекорда, а он закрывается только временем. Каждый день, когда воркер не работает где-то
постоянно, — день, которого в этой истории не будет.

## Правило про секреты, прежде чем таблица

**Никогда не вставляйте секрет в чат, в issue или в коммит — включая `DATABASE_URL`, в котором
лежит пароль.** Они вводятся прямо в хранилище площадки: `fly secrets import` и переменные окружения
Vercel. Оба шифруют их у себя, и ни один не проходит через этот репозиторий.

Сейчас корневой `.env` держит весь набор открытым текстом на одном ноутбуке. После того как
площадки их получат, локальные копии того, что попало в продакшн, надо удалить.

Кому что нужно — проверено по коду, а не по устаревшему `.env.example`:

| Переменная                     | web | воркер | Примечание                                                             |
| ------------------------------ | :-: | :----: | ---------------------------------------------------------------------- |
| `DATABASE_URL`                 |  ●  |   ●    | Единственная переменная, которая воркеру действительно обязательна     |
| `SESSION_SECRET`               |  ●  |        | Сгенерировать заново; значение до переустановки скомпрометировано      |
| `ENCRYPTION_KEY`               |  ●  |        | Шифрует Anthropic-ключи пользователей в базе                           |
| `ANTHROPIC_API_KEY`            |     |   ●    | Наш, для тех, у кого нет своего                                        |
| `AGENT_PRIVATE_KEY`            |     |   ●    | **По одному на сеть.** Должен выводиться в `serviceAgent` этой сети    |
| `NETWORK`                      |     |   ●    | В `fly.testnet.toml`, не секрет                                        |
| `DRY_RUN`                      |     |   ●    | В `fly.testnet.toml`. Пусто = симуляция; непонятное = отказ стартовать |
| `CREDITS_WATCHER_START_BLOCK`  |     |   ●    | По сети. Не задано = «с текущей головы цепи»                           |
| `RPC_URL_MAINNET` / `_TESTNET` |  ○  |        | Необязательны; иначе публичный RPC из `config.ts`                      |
| `RPC_URL`                      |     |   ○    | Собственный у воркера, одна сеть                                       |
| `VITE_APP_URL`                 |     |        | Только `apps/site` — адрес продуктового приложения                     |

`RPC_URL_MAINNET` необязателен, но поставить стоит: публичный мейннет-RPC стоит за Cloudflare и
отбивает батчевые JSON-RPC POST-запросы, возвращая HTML-заглушку. Платный эндпоинт убирает целый
класс отказов, которые иначе выглядят как случайные ошибки RPC.

Оба приложения явно загружают корневой `.env` (`next.config.ts`, `agent/src/config.ts`). На
площадках этого файла нет, а dotenv на несуществующем пути просто ничего не делает и **не
перезаписывает** уже заданные переменные — так что секреты площадки выигрывают, и обе эти строки
не нуждаются в особом случае для продакшна.

## Порядок действий

Каждый клик и каждая команда, по порядку. Примерно 40 минут. Ничего необратимого здесь нет: не то
значение — это пере-вставка, а не деплой заново.

Базы раньше того, что из них читает; воркер раньше веб-приложения, чтобы отказы первого деплоя
пришлись туда, куда никто не смотрит.

Два секрета надо **сгенерировать**, один — **скопировать из локального `.env`**, один взять у
Anthropic. Разница важная, поэтому на каждом шаге оговорена.

### Шаг 1 — Postgres на Neon

1. Откройте <https://neon.tech> и зарегистрируйтесь через GitHub.
2. **Create project.** Имя `puno`. Регион поближе к себе; версию Postgres оставьте по умолчанию.
3. На странице проекта найдите блок **Connection string** (или кнопку **Connect**) и включите
   переключатель **Pooled connection**.
4. Скопируйте.

Это и есть `DATABASE_URL`: одна строка, в которой сразу адрес сервера, база, логин и пароль.
Больше ничего для доступа не нужно — и поэтому же она равносильна паролю.

```
postgresql://neondb_owner:ПАРОЛЬ@ep-cool-name-12345-pooler.eu-central-1.aws.neon.tech/neondb?sslmode=require
             └─ логин ──┘└пароль┘└──────────────────── хост ────────────────────────┘└база─┘
```

**Признак того, что взята правильная: в имени хоста есть `-pooler`.** Если его нет, скопировано
прямое подключение — вернитесь и включите переключатель. Разница не косметическая: Vercel
serverless открывает своё соединение на каждый запрос и почти сразу закрывает, прямое подключение
упрётся в лимит Postgres на десятках одновременных, и приложение начнёт отдавать 500 под
нагрузкой — то есть не сразу, а когда появятся люди.

Отдельно проверять строку не нужно: **шаг 3 и есть проверка.** Если `db:migrate` дошёл до
`Migrations applied.`, строка верна; если нет — он упадёт на подключении, ничего не изменив.

`CreditsDb` не зависит от драйвера, а схема — обычный Postgres, так что ничего специфичного для
провайдера здесь нет; Supabase подойдёт так же.

**В этой строке пароль. Не вставляйте её в чат, в issue и в файлы репозитория.** Она попадает
только в хранилища Fly и Vercel, на шагах ниже.

### Шаг 2 — сгенерировать два секрета для веба

Выполните дважды, ответы держите порознь:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

Первый — `SESSION_SECRET` (подписывает cookie входа), второй — `ENCRYPTION_KEY` (AES-256-GCM над
чужими Anthropic-ключами, 32 байта в hex).

Именно **новые**, а не из локального `.env`: продакшн-база стартует пустой, значит старым ключом
ничего не зашифровано, а ключ, защищающий чужие секреты, не должен лежать на машине разработки.

Это намеренно два разных значения — утечка подписывателя cookie не должна задевать ключ, которым
защищены сохранённые API-ключи.

### Шаг 3 — создать таблицы и поставить курс

База в Neon пустая, а приложение обращается к ней почти на каждой странице. Задеплоить до этого
шага — получить 500 на всём.

Миграции обычно выполняет `release_command` у Fly, поэтому если Fly откладывается, их надо
прогнать руками один раз с этого ноутбука. В PowerShell нет префикса переменных в строке команды,
так что сначала присвоение:

```powershell
cd C:\Users\chaiz\Desktop\puno-agent-main
$env:DATABASE_URL = 'СТРОКА_ИЗ_NEON_ЦЕЛИКОМ'
pnpm.cmd --filter @puno/agent db:migrate
pnpm.cmd --filter @puno/agent set-rate -- 0.00001 --note "testnet launch"
Remove-Item Env:\DATABASE_URL
```

**Одинарные кавычки, и они обязательны — заменяйте только то, что внутри них.** Вставленная без
кавычек строка падает на `AmpersandNotAllowed`: `&` перед `channel_binding` PowerShell считает
оператором. А двойные кавычки опаснее отсутствия — они раскрывают `$`, поэтому пароль, содержащий
`$`, будет молча обрезан, и ошибка придёт про аутентификацию, то есть укажет не туда. Внутри
одинарных кавычек не значат ничего ни `&`, ни `$`. Если в пароле есть одинарная кавычка, продублируйте
её: `''`.

`cd` в первой строке тоже обязателен: PowerShell открывается в домашнем каталоге, а `--filter`
разрешается только изнутри воркспейса. Из `C:\Users\<вы>` команда падает на
`ERR_PNPM_NO_PKG_MANIFEST` — pnpm не видит ни `package.json`, ни, соответственно, скрипт.
Отдельный `pnpm install` не нужен: зависимости уже установлены в дереве проекта.

**`pnpm.cmd`, а не `pnpm` — не опечатка.** На свежей Windows политика выполнения сценариев по
умолчанию `Restricted`, и обёртка `pnpm.ps1` из глобального npm-каталога не запускается:
_«Невозможно загрузить файл … pnpm.ps1, так как выполнение сценариев отключено»_,
`PSSecurityException`. Батник `pnpm.cmd` лежит рядом и политикой не проверяется вообще, поэтому
работает без изменения настроек машины. Если удобнее один раз включить сценарии —
`Set-ExecutionPolicy -Scope CurrentUser RemoteSigned` (права администратора не нужны), но помните,
что политика выполнения не является средством защиты: её обходит любой `-ExecutionPolicy Bypass`,
и Microsoft описывает её как защиту от случайного запуска, а не от злоумышленника.

В Git Bash проблемы нет вовсе, и там работает однострочная форма:
`DATABASE_URL="..." pnpm --filter @puno/agent db:migrate`.

Переменная, заданная в оболочке, перебивает корневой `.env` — dotenv никогда не перезаписывает уже
существующее, — поэтому случайно попасть в локальную базу нельзя. Последняя строка убирает её,
чтобы следующая команда в том же терминале не ушла молча в продакшн.

Ожидается `Migrations applied.` и тринадцать таблиц. Скрипт называется `db:migrate`, а не
`migrate`.

Курс ставится отдельной командой, потому что живёт в Postgres, а не в конфиге. Без него
`/api/pricing` вернёт `tokenPrice: null`, и все цены свалятся обратно в доллары — лендинг тихо
перестанет показывать PUNO.

### Обновление курса — регулярная обязанность, пока пул не читается

Курс годен для начисления **72 часа** (`MAX_OVERRIDE_AGE_MS`). Это не срок, к которому надо
успеть, а запас: **возраст считается от самой свежей записи, поэтому `set-rate` обнуляет отсчёт в
любой момент.** Частота ничем не ограничена — `checkRateChange` проверяет только отношение цен.

**Ставьте раз в сутки, по своему расписанию, а не по предупреждению в логе.** Тогда запас — двое
суток, и можно забыть два дня подряд. Формула простая: `запас = окно − интервал обновления`, и
именно поэтому окно расширили с 24 часов: при ежедневном обновлении 24 часа дают запас ноль.

Осторожно с редким расписанием: **с утра пятницы до утра понедельника ровно 72 часа**, то есть
режим «пн / ср / пт» стоит точно на границе без запаса.

Команда:

```powershell
cd C:\Users\chaiz\Desktop\puno-agent-main
$env:DATABASE_URL = 'СТРОКА_ИЗ_NEON_ЦЕЛИКОМ'
pnpm.cmd --filter @puno/agent set-rate -- <цена> --note "почему"
Remove-Item Env:\DATABASE_URL
```

**Какую цену вписывать.** На тестнете — ту же, `0.00001` (поднято с `0.000001` 2026-08-17 ради
читаемости чисел, не ради точности): токен там мок, цены у него нет. **На
мейннете повторять прошлое число нельзя** — посмотрите текущую цену в пуле PUNO/USDG и впишите её.
Несвежее число бьёт по вкладчику: карточка попросит отправить токенов на $60 и начислит $20, а
доказать это он сможет только нашим же логом. Прочитайте таблицу предпросмотра перед записью —
это единственная проверка перед тем, как число станет ценой для всех.

**Что происходит при истечении — ничего необратимого.** Индексатор откатывает курсор и не двигается
за событием, которое не смог оценить; `/api/billing/claim` отвечает отказом с текстом «токены в
безопасности на цепи»; `TopUpCard` перестаёт называть сумму к отправке. Цены на лендинге живут ещё
до седьмых суток (`MAX_DISPLAY_AGE_MS`). Депозиты переигрываются, как только курс поставлен.

Воркер предупреждает в логе строкой `[rate]`, начиная с 24 часов остатка. Появилась — значит цикл
обновления уже пропущен, но сутки в запасе есть.

**Замена этому ритуалу — `readPoolTwap()`**, чтение пула вместо человека. Отложено сознательно, см.
`LAUNCH-CHECKLIST.md`.

### Шаг 4 — воркер на Fly

**Fly требует карту.** Постоянный бесплатный тариф закончился в 2024 году; новому аккаунту дают
пробу на два VM-часа или семь дней, что кончится раньше, дальше каждая машина платная. Одна
круглосуточная `shared-cpu-1x` на 256 МБ — около **$1.94/мес**, на 512 МБ — около **$3.20**.
Помесячных планов нет, тарификация посекундная.

Если платить пока не хочется — переходите к шагам 5 и 6: у Vercel бесплатный тариф без карты, и
публичный продукт поднимется без воркера. Цена отсрочки точная: бесплатное демо работает только
пока включён ноутбук, и трек-рекорд не копится.

Установка `flyctl` (PowerShell, один раз):

```powershell
iwr https://fly.io/install.ps1 -useb | iex
```

Дальше — **из корня репозитория**, потому что контекст сборки это рабочий каталог:

```powershell
cd C:\Users\chaiz\Desktop\puno-agent-main
fly auth signup      # или: fly auth login
fly apps create puno-worker-testnet
```

`cd` в блоке не для красоты. Без него `flyctl` не найдёт конфиг на следующих командах и скажет
_«config file not found at specified path»_, попутно попробовав путь как каталог, — сообщение
про `-c`, а причина в каталоге. И даже угадав конфиг, сборка из `apps/agent` собрала бы образ без
корневого лок-файла и без `packages/shared`, потому что `Dockerfile` копирует их из корня.

**`fly apps create`, а не `fly launch` — проверено 2026-08-17 на собственной шкуре.** `launch`
считает, что конфиг принадлежит ему: он переписал `fly.testnet.toml`, подменил `app` на
сгенерированное `puno-worker-testnet-ambergris-meadowstone-6884` и снёс все шестьдесят строк
комментариев, объясняющих, почему `DRY_RUN` здесь `false` и почему нельзя поднимать вторую
машину. Функциональные значения он сохранил все до единого — но объяснение того, чего стоит
ошибка, ценнее самих строк, а восстанавливается только из git. `apps create` не создаёт и не
трогает `fly.toml` вовсе; флаг `--save` у неё для этого и существует, и он нам не нужен, потому
что нужное имя в файле уже написано.

Если `launch` всё-таки был запущен — `git checkout -- apps/agent/fly.testnet.toml` возвращает
файл, а лишнее приложение убирается через `fly apps destroy <имя>`. Сверьте имя посимвольно:
удаление не спрашивает второй раз.

`--ha=false` на `deploy` ниже — не опция, а обязательство. Fly по умолчанию поднимает **две**
машины, а два воркера тикают одних и тех же агентов одновременно: два списания за скрининг с
одного баланса и две гонки сделок из одного вольта. Поля с количеством машин в `fly.toml` нет,
поэтому флаг нужен на каждом `deploy`, всегда.

Если команда падает с _«requested machine count exceeds organization limit»_ — это шлюз оплаты,
а не количество машин: у организации без привязанной карты лимит равен нулю.

Теперь секреты. `AGENT_PRIVATE_KEY` — единственный, который нельзя сгенерировать заново: каждый
тестнетовый вольт вооружён конкретным адресом, значит воркер обязан держать именно этот ключ.
Берётся из строки `AGENT_PRIVATE_KEY` локального корневого `.env` — проверено 2026-08-16, что он
выводится в `0x389AA9c066854a1e1A62a9F49910760a8D010adD`, то есть в `NETWORKS.testnet.serviceAgent`.

**Не `fly secrets set`, а `import` со стандартного ввода.** Причина не в удобстве: PowerShell
записывает каждую введённую команду в `ConsoleHost_history.txt`, поэтому секрет, переданный
аргументом, остаётся в открытом виде в файле, который переживёт сессию. Введённое в stdin туда не
попадает. Проверено 2026-08-16 — файл на этой машине уже содержал строку подключения Postgres
после шага 3.

```powershell
fly secrets import -a puno-worker-testnet
```

Команда ждёт ввода. Вставьте три строки, затем **Ctrl+Z и Enter** (это конец ввода в Windows):

```
DATABASE_URL=<из шага 1>
ANTHROPIC_API_KEY=<console.anthropic.com → API keys>
AGENT_PRIVATE_KEY=<AGENT_PRIVATE_KEY из локального .env>
```

Кавычки не нужны и вредны: в формате `NAME=VALUE` они станут частью значения.

**Дождитесь пустой строки без приглашения `PS C:\...>` прежде чем вставлять.** Если команда не
запустилась — например, приложения ещё нет, проверяется через `fly apps list`, — вставка уйдёт в
сам PowerShell, и он попытается разобрать её как команду. Спотыкается он об `&` в
`?sslmode=require&channel_binding=require`: _«Амперсанд (&) не разрешен»_, `AmpersandNotAllowed`.
Сообщение указывает на строку подключения, хотя со строкой всё в порядке — не запустилась команда.
Пароль при этом не разглашается: PowerShell показывает фрагмент вокруг `&`, то есть часть после
`@`.

Если интерактивная вставка не даётся, есть неинтерактивный путь. Перенаправление ввода через `<`
в PowerShell 5.1 не работает, поэтому через конвейер:

```powershell
notepad "$env:TEMP\puno-secrets.txt"     # вставить три строки, сохранить, закрыть
Get-Content "$env:TEMP\puno-secrets.txt" | fly secrets import -a puno-worker-testnet
Remove-Item "$env:TEMP\puno-secrets.txt"
```

Заодно почистите то, что уже записалось на шаге 3 (неудачная команда пишется в историю так же,
как удачная):

```powershell
Remove-Item "$env:APPDATA\Microsoft\Windows\PowerShell\PSReadLine\ConsoleHost_history.txt"
```

`CREDITS_WATCHER_START_BLOCK` **не задавайте**. Пусто означает «с текущей головы цепи», что верно
для базы, которая начинается пустой; записанный там старый тестнетовый блок переиграл бы месяцы
исторических депозитов в несуществующие аккаунты.

```powershell
fly deploy . --ha=false -c apps/agent/fly.testnet.toml
fly logs -a puno-worker-testnet
```

**Точка после `deploy` и путь в `-c` отсчитываются от разных мест — так и надо.** Проверено
сборкой 2026-08-17. Точка задаёт рабочий каталог, он же контекст сборки: корень репозитория, иначе
`COPY pnpm-lock.yaml` из `Dockerfile` не найдёт файла. А `dockerfile` внутри `fly.testnet.toml`
разрешается от каталога **этого файла**, а не от рабочего, поэтому там написано просто
`Dockerfile`. Пока там стояло `apps/agent/Dockerfile`, `flyctl` складывал одно с другим и искал
`apps/agent/apps/agent/Dockerfile`; позиционный аргумент на это не влияет — проверено.

Убедиться в сборке, ничего не запуская, можно флагом `--build-only`. Для первого прогона это
стоит сделать: он проверяет `Dockerfile` и контекст, но не поднимает воркер, а значит не начинает
торговать.

В логе загрузки три строки, каждая ловит свою ошибку:

- `Signing as 0x389AA9c066854a1e1A62a9F49910760a8D010adD` — адрес, которым вооружены вольты.
  **Сверьте посимвольно**: это правило буфера обмена, и ошибка здесь дорогая — воркер с чужим
  ключом отсканирует, решит, **спишет с пользователя** и только потом откатится на цепочке с
  «not authorized», по разу на агента за тик. При несовпадении процесс откажется стартовать, и
  этот отказ — сработавшая защита.
- `Deposit watcher enabled — PunoCredits at 0x…`, либо `idle`, если у сети нет биллингового
  контракта.
- `[rate]` — если такой строки нет вовсе, курс свежий. Предупреждение означает, что начисления
  вот-вот встанут или уже встали.

**Одна машина, никогда две.** `tickAllAgents()` обходит всех живых агентов без лизы и блокировки.
Не масштабируйте до 2, пока лиза не появится.

Второе: `VITE_APP_URL` подставляется Vite **на сборке**, а не в рантайме — значение лежит

| -------------------------------- | ------------------- | ----------------------------------------------- |

### Мейннет: что можно сейчас, а что только в день T-0

**Уточнено 2026-08-17.** Здесь стояло «не создавайте мейннет-воркер и не кладите мейннет-ключи
никуда». Запрет был прав в главном и слишком широк в одном месте, и разница между этими двумя
вещами — работает ли машина.

**Машину поднимать нельзя, и это не изменилось.** У `NETWORKS.mainnet` нет `punoCredits`, мейннет
закрыт по построению (`whyClosed()`), индексатор депозитов возвращается сразу же, а агентов на 4663
нет и быть не может, пока визард закрыт. Работающий воркер там ничего не делает и стоит денег.

**А вот ключ переложить можно и стоит уже сейчас.** `fly secrets set` на приложении без машин
ничего не запускает — он показывает `Secrets are staged for the first deployment` и хранит значение
зашифрованным до первого деплоя. Ровно это мы видели на тестнете. Так что ключ уходит с ноутбука в
хранилище Fly, машина не поднимается, мейннет остаётся закрытым.

Почему это стоит сделать заранее, а не в день T-0: `.env.mainnet.local` — это приватный ключ
открытым текстом на машине, которую в августе находили с бэкдором. Тянуть с этим до дня, когда и
без того двадцать шагов, — худший из возможных моментов.

**Важно: это перенос, а не копирование.** Пока локальный файл не удалён, ключ лежит в двух местах,
и экспозиция не уменьшилась, а выросла. Удаление локального файла — часть шага, а не уборка потом.

```powershell
cd C:\Users\chaiz\Desktop\puno-agent-main
fly apps create puno-worker-mainnet
```

Секрет — **через stdin, не аргументом командной строки**. В PowerShell аргументы попадают в
`ConsoleHost_history.txt`, и приватный ключ там останется навсегда.

**Не вставляйте команду и её stdin одним блоком — это не работает и не может работать.** PowerShell
разбирает весь вставленный текст **до** того, как выполнит первую строку, поэтому строка с
`DATABASE_URL=...` будет разобрана как команда, а не отдана запущенному `fly secrets import`.
Падает это на `AmpersandNotAllowed` (`&` перед `channel_binding`), что выглядит как проблема с
кавычками и ею не является. Поймано трижды.

Устойчивая к вставке форма — присвоение и пайп, все строки валидный PowerShell:

```powershell
$env:DATABASE_URL = 'СТРОКА_ИЗ_NEON_ЦЕЛИКОМ'
"DATABASE_URL=$env:DATABASE_URL" | fly secrets import -a puno-worker-mainnet
Remove-Item Env:\DATABASE_URL
Remove-Item (Get-PSReadlineOption).HistorySavePath
```

Кавычки разные, и обе намеренно: одинарные в присвоении, потому что внутри них `&` и `$` не значат
ничего; двойные в пайпе, потому что там `$env:DATABASE_URL` обязан раскрыться, а `&` к тому моменту
уже внутри строкового литерала.

Второй способ, если предпочитаете интерактивный: запустить `fly secrets import -a <app>` **отдельной
вставкой**, дождаться, пока команда начнёт ждать ввода, и только потом вставлять строки — по одной,
затем Enter на пустой строке:

```
AGENT_PRIVATE_KEY=<приватный ключ из .env.mainnet.local>
DATABASE_URL=<та же строка Neon, что у web и у тестнет-воркера>
ANTHROPIC_API_KEY=<ключ>
```

**Ровно три, и список проверен, а не составлен по памяти.** Работающий тестнет-воркер держит эти
же три и ничего больше, а в схеме `apps/agent/src/config.ts` обязателен один `DATABASE_URL` —
остальное необязательно или имеет значение по умолчанию.

**`ENCRYPTION_KEY` сюда не входит, и раньше здесь было написано обратное.** Исправлено 2026-08-17:
он не встречается ни в `apps/agent`, ни в `packages/shared` — только в `apps/web`
(`lib/crypto.ts`, `lib/session.ts`). Причина, по которой воркеру он не нужен, неприятная и записана
в `LAUNCH-CHECKLIST.md`: BYOK не доведён до конца, воркер читает колонку с чужим ключом только как
«есть/нет» и все вызовы делает нашим ключом. Когда это починят, `ENCRYPTION_KEY` здесь появится.

**`NETWORK` здесь быть не должно.** Он уже задан в `[env]` внутри `fly.mainnet.toml`, а секрет
Fly перекрывает `[env]` — значение в файле стало бы мёртвым, и всякий, кто прочитает файл, поверит
ему напрасно. Настройка, решающая, на какой цепи идёт торговля, должна жить ровно в одном месте, и
это место — коммит, а не шелл.

**`DATABASE_URL` обязан быть той же строкой Neon**, что у `apps/web` и у тестнет-воркера: база
одна на обе сети. Это проверяемо, не читая значений — `fly secrets list` печатает дигест, и он
детерминирован по значению, так что совпадение дигестов у двух приложений доказывает совпадение
строк.

Затем удалите локальный файл и очистите историю:

```powershell
Remove-Item .env.mainnet.local
Remove-Item (Get-PSReadlineOption).HistorySavePath
```

Проверка, что ключ на месте и что это тот ключ: `fly secrets list -a puno-worker-mainnet` покажет
имена и дайджесты, но не значения. Что ключ выводится в правильный адрес, воркер докажет сам при
первом старте — `serviceAgent.ts` отказывается загружаться при несовпадении, в бумажном режиме тоже.

**Деплой (`fly deploy`) — только в день T-0**, после того как `PunoCredits` существует и его адрес
попал в `config.ts`. До этого приложение остаётся пустым: `fly apps list` покажет его без машин.

## Известные пробелы

**Нет health-эндпоинта.** Воркер ничего не обслуживает, поэтому Fly видит только, жив ли процесс —
зависший, но не упавший воркер выглядит здоровым. Стоит сделать маленький HTTP-эндпоинт до того,
как здесь появятся платящие пользователи; сейчас намеренно не сделан, потому что это новая
поверхность у сервиса, у которого её нет вовсе.

**Нет мягкого завершения.** Найдено первым же перезапуском 2026-08-16: в `main.ts` нет
`process.on("SIGINT")` и `SIGTERM`, поэтому Fly убивает воркер посреди работы на каждом деплое.
Почти всё это переживает: списания идемпотентны по `tradeId`, курсор индексатора не двигается за
неначисленным, `pending`-строки триалов остаются. Незакрытым остаётся окно между отправкой сделки
и записью её статуса — сделка в цепи, база о ней не знает, и повторная попытка после рестарта уже
не безобидна. Нужен обработчик, который перестаёт заводить новые тики и ждёт текущий. **Оба
сигнала**: `Dockerfile` писался под `SIGTERM`, а Fly шлёт `SIGINT`.

`DRY_RUN` **отсутствует**, а не выставлен. По `dry-run.ts` незаданное значение означает симуляцию,

в отдельном коммите в день T-0, чтобы момент, когда продукт начал торговать настоящими деньгами,
был датированной записью в истории, а не флагом, который кто-то выставил из шелла. Полагаться на
обратное по умолчанию нельзя: бумажный режим не безобиден, когда есть пользователи — `runTick`
складывает процессный флаг с `agents.dry_run` по ИЛИ, так что воркер в бумажном режиме переводит в
бумажный **всех** агентов независимо от выбора владельца, страница агента при этом показывает
выбранный им режим, и пользователь платит за решения, которые никогда не превратятся в сделку.
